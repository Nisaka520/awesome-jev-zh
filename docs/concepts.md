## 一、System One 到底新在哪

名字取自卡尼曼《思考，快与慢》里的**系统一**：快速、自动、直觉的那套思维。系统二才是慢的、费力的、会推理的那套。

过去三年所有的工程努力，都是在用**系统二**（一个会写文章的 LLM）去干**系统一**的活：

```
这个工单属于哪个组？
  → 拼一段 prompt
  → 让一个能写十四行诗的模型逐 token 生成
  → 它输出 {"department": "billing"}（但愿它没顺手包一层 Markdown 代码块）
  → 你写 JSON 解析 + schema 校验 + 重试 + fallback
  → 800ms 过去了，花了 $0.003
```

荒谬之处在于：**你要的只是三选一。** 生成能力在这里 100% 是浪费，而且是有害的浪费——因为生成意味着它可能生成出你没定义的东西。

System One 模型把这件事从根上改了：合法输出在 schema 里**提前穷举完**，模型做的不是「生成一个答案」，而是**在候选上做一次受限打分**。所以：

| | 生成式做法 | System One 做法 |
| :-- | :-- | :-- |
| 输出空间 | 整个词表的所有序列 | 你给的 N 个候选 |
| 解析 | 要写 JSON 解析 + 校验 + 重试 | 没有解析这回事 |
| 违约 | 可能输出 schema 外的东西 | 结构上不可能 |
| 延迟 | 和输出长度成正比 | 一次并行 pass，与问题数量几乎无关 |
| 并行提问 | 每题一次调用，或塞进一个大 prompt 互相干扰 | 同一份 state 上并行、隔离求值 |

**这不是「更小更快的 LLM」，是把问题重新定义了一遍。** 这也是官方博文 [The Bitterest Lesson](https://typesafe.ai/blog/bitterest-lesson) 的论点：优化错了任务，规模再大也盖不过去。

## 二、RLCD：为什么要换一套训练目标

三种对齐方法的目标函数完全不同：

| 方法 | 全称 | 优化什么 | 结果 |
| :-- | :-- | :-- | :-- |
| **RLHF** | 人类反馈强化学习 | 人类**更喜欢**哪个回答 | 回答讨喜、流畅、有礼貌 |
| **RLVR** | 可验证奖励强化学习 | 答案**对不对**（数学、代码可验证） | 推理能力强 |
| **RLCD** | 校准决策强化学习 | 概率**诚不诚实** | 说 70% 就真有 70% |

RLHF 有个众所周知的副作用：**偏好对齐会破坏校准。** 一个被训练成「让人满意」的模型，倾向于表现得比实际更确定——因为犹豫的回答不讨喜。这对聊天是优点，对自动化是灾难：你没法用它的「我 90% 确定」去做门控，因为那个 90% 不是真的 90%。

TypeSafe 的立场（见 [AI: too good to be true, too bad to be useful](https://typesafe.ai/blog/ai-too-good-to-be-true-too-bad-to-be-useful-typesafe-ai)）就是：**自动化流程不该用偏好对齐过的聊天模型**。RLCD 直接把「概率诚实」作为优化目标，换来的就是那个可以拿来写 `if` 的 `confidence`。

> ⚠️ 这是厂商的技术主张。RLCD 目前没有公开论文，校准质量在你自己的数据上究竟如何，**必须自己量**——[上手指南第三节](quickstart.md#三置信度门控用对-jev-的分水岭)的分桶表就是干这个的。

## 三、「不可能幻觉」的准确含义

这句话被传得最广，也被误解得最狠。

**它的意思是：**
- ✅ 不可能输出你没定义的选项
- ✅ 不可能违反 schema、不可能类型错误
- ✅ 不可能编造一个不存在的函数名、不存在的链接、不存在的 DOM 元素

**它不意味着：**
- ❌ 判断一定对
- ❌ 不会选错选项
- ❌ 中文场景和英文场景一样准

换句话说，它消除的是**结构性幻觉**（编出不存在的东西），不是**判断错误**。后者靠置信度门控兜，不是靠模型保证。

这个区分在实践中极其重要。Wikiracing demo 之所以被反复提起，正是因为它展示的是**结构性保证**：在几百个链接里选下一跳，**永远不会选一个页面上不存在的链接**——而一个 LLM 会。至于选的那一跳好不好，那是另一回事。

## 四、校准概率怎么读

三个数字，别混：

| 字段 | 含义 | 怎么用 |
| :-- | :-- | :-- |
| `choice` / `score` / `noul` | 答案本身 | 拿去执行 |
| `confidence` | 模型对这个答案有多确信 | **写门控阈值** |
| `probabilities` | 每个候选的完整概率分布 | 诊断「这题是不是本来就难」 |

**`confidence` 低有两种完全不同的原因，`probabilities` 能分辨：**

```
情况 A：probabilities = {billing: 0.45, technical: 0.42, sales: 0.13}
  → 前两名咬得很紧。这条工单本身就跨两个组，人来判也会犹豫。
  → 对策：上抛人工，或者承认你的分类体系本身有重叠。

情况 B：probabilities = {billing: 0.38, technical: 0.31, sales: 0.31}
  → 三个都低，分布接近均匀。模型基本没抓到信号。
  → 对策：state 信息不够（要补上下文），或者判据写得太模糊。
```

**校准的操作性定义**：把所有 `confidence ∈ [0.7, 0.8)` 的样本挑出来，它们的实际准确率应该落在 70–80%。**不满足就是没校准**，那你的阈值就是假的。这张表要在自己的数据上跑，跑完才算真的会用 Jev。

## 五、为什么「问题要原子」

官方反复强调：**atomic questions, composed in code**（问题尽量原子，组合逻辑写在代码里）。这不是风格偏好，是架构约束的直接推论。

因为**同一次请求里的问题是并行、隔离求值的**——问题 B 看不见问题 A 的答案。所以任何「先判断 X，如果 X 成立再判断 Y」的逻辑，天然属于你的代码，不属于一次请求。

更重要的是可维护性：

```python
# ❌ 复合问题：出错了你不知道错在哪一环
Score(instructions="这段代码的整体质量", criteria=["差", "中", "好"])

# ✅ 原子问题：每个维度能单独验证、单独调阈值、单独换权重
{
  "readability":  Score(instructions="命名和结构的可读性", criteria=[...]),
  "has_bug":      Noul(instructions="这段代码存在明显的逻辑错误"),
  "test_covered": Noul(instructions="关键分支有对应的测试"),
}
# 权重在你的代码里，随时能改，不用重新调 prompt
quality = 0.3 * readability + 0.5 * (1 - has_bug) + 0.2 * test_covered
```

第二种写法的好处：**权重是代码里的常量，不是模型里的黑箱。** 产品说「先别那么看重测试覆盖」，你改一个数字就行，不用重新验证模型行为。这就是[组合打分模式](https://docs.typesafe.ai/patterns/composite-scoring)。

### 这一条有硬数据支撑

[jev-phishing-bench](https://github.com/anisselbd/jev-phishing-bench) 在 2000 封钓鱼邮件上做过一次很说明问题的对照：

| 用法 | 准确率 |
| :-- | :-- |
| 直接问一个复合问题「该不该点这个链接」 | **62.6%** |
| 同一次调用里拆成 5 个原子信号问题 + 代码里做逻辑回归 | **95.0%** |

**同一个模型、同一批数据、同一次 API 调用，差了 32 个百分点。** 差别只在于「让模型做判断」还是「让模型提供信号、由你的代码做判断」。

这就是「问题要原子」不是风格建议而是正确性问题的原因。顺带一提，那份评测里还有盆冷水：一条两行的正则规则在同一数据集上有 91.8%，比 Jev 最好的单信号还高——**上新东西之前先跑传统基线**，见主列表的[冷静看待](../README.md#-冷静看待争议与已知毛边)。

## 六、把现有 LLM 流程改造成 Jev 流程：四步法

假设你手上有一个跑着的 LLM 流程，想看看能省多少。

### 第 1 步 · 找出「伪装成生成的判断」

把流程里每一次 LLM 调用列出来，逐个问：**这次调用的输出，最终被代码怎么用了？**

| 输出的去向 | 结论 |
| :-- | :-- |
| 被解析成一个枚举值，然后 `if` / `switch` | 🎯 **换 Choice** |
| 被解析成一个数字，然后比大小 / 排序 | 🎯 **换 Score** |
| 被解析成 true/false | 🎯 **换 Noul** |
| 从固定列表里选一个（工具、技能、模型、元素） | 🎯 **换 Choice** |
| 原样展示给用户看 | ✋ 留给 LLM |
| 作为下一次 prompt 的输入文本 | ✋ 留给 LLM |

经验上，一个成熟的 Agent 流程里 **60–80% 的 LLM 调用属于前四类**。这就是 [fast-jev-compaction](https://github.com/tamaratran/fast-jev-compaction)、[winnow](https://github.com/GhalebDweikat/winnow)、[jev-router](https://github.com/gargpratyush/jev-router) 这批工具的共同发现。

### 第 2 步 · 把 prompt 拆成原子问题

原来一个大 prompt 里塞的「请判断意图、情绪、紧急度，并输出 JSON」，拆成三个独立问题。选项和量表从你原来 prompt 里的描述直接搬过来当 `criteria`。

### 第 3 步 · 合并成一次扇出

第 2 步拆出来的问题，**全部放进同一次请求**。因为输出免费、state 只算一次钱，多问不花钱。顺便把「以前因为太贵所以没问」的问题也加上——这一步经常能白捡新功能。

### 第 4 步 · 加门控，量阈值

每个决策点配一条降级路径，然后在真实数据上跑置信度分桶表定阈值。**这一步做完才算改造完成**，跳过它等于把没校准的概率当成校准的用。

## 七、它不能做什么

写在最后，免得改造改过头：

| 需求 | 能不能 |
| :-- | :-- |
| 生成文本、代码、摘要 | ❌ 完全不会，这是设计不是缺陷 |
| 给出判断理由 | ❌ 只给概率，不给解释 |
| 多步推理、链式思考 | ❌ 问题之间隔离，天生没有链 |
| 开放式抽取（候选未知） | ⚠️ 要先出候选再选 |
| 图像、音频、视频输入 | ❌ 当前只支持纯文本 |
| 超长文档一次吃下 | ⚠️ 64k 上限，state 部分 32k |
| 替代你的向量检索 | ⚠️ 小规模重排序可以，大规模召回不行——先 BM25/向量出短名单，再让它排 |
| 保证判断正确 | ❌ 靠门控兜，不靠模型 |

**一句话总结心法：**

> 让 LLM 去做只有 LLM 能做的事（生成、解释、开放推理），
> 把所有「其实只是在做选择题」的调用交给 Jev，
> 把组合逻辑、权重和阈值牢牢握在你自己的代码里。
