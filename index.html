一个不说话的模型

你给它一段文字和几个带类型的问题，
它返回代码能直接用的值——不写一个字。

Jev · TypeSafe System One
2026.09.15 发布 · GITHUB.COM/YZFLY/AWESOME-JEV-ZH
01

它不是更小更快的 LLM，是另一类东西

大语言模型：你给它 prompt，它逐 token 生成一串字符串。你再写代码去解析、校验、重试。它可能输出你没定义的东西。

Jev：你给它一段 state 和一组带类型的问题，它一次并行答完，返回的值本来就在你给的集合里。没有解析这一步，因为它压根没生成字符串。

TypeSafe 管这类模型叫 System One，取自卡尼曼的「系统一」——快速、直觉的那套思维。训练方法叫 RLCD，优化目标是概率诚实，不是人类偏好。

输出你给的选项之一 / 一个分数 / 一个 0–1 概率
延迟70–500ms，一次并行 pass 答完所有问题
输入价格$0.042 / MTok
输出价格不计费
会写代码吗不会。这是设计，不是缺陷
来源：官方 Models 文档与发布博文

03

真实请求：一次调用，三个问题

# pip install typesafe-sdk
from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

client = TypeSafeClient()        # 读 TYPESAFE_API_KEY

r = client.system_one(
    state="我被重复扣款两次了，三天没人理，再不退款我就投诉。",
    questions={
        "department": Choice(
            instructions="这个工单该给哪个组",
            criteria={
                "billing":   "支付、扣款、订阅、退款",
                "technical": "Bug、集成失败、服务不可用",
                "sales":     "定价、试用、商务咨询",
            },
        ),
        "frustration": Score(
            instructions="客户的不满程度",
            criteria=["平静陈述", "有情绪但讲道理", "非常愤怒"],
        ),
        "is_urgent": Noul(
            instructions="这条消息表达了紧急或时间压力"
        ),
    },
)

criteria 的 key 给代码用，value 给模型看。key 写得像标识符，value 写得像人话，两边都别省。

Noul 写陈述句，不写问句。写「用户在抱怨」，别写「用户在抱怨吗？」

Score 的档位要能用眼睛验证。「好 / 中 / 差」会飘，上面那三档才稳。

三个问题在同一次请求里对同一份 state 并行求值，彼此看不见对方的答案。

choice一定是你给的三个 key 之一。它没有能力返回第四个值
score小数，不是档位序号。1.035 落在「有情绪但讲道理」附近，比三档本身更细

05

上一页那个 0.596，正是不该直接执行的例子

department 的置信度只有 0.596。这条工单同时提到了扣款和没人理，本来就跨 billing 与 technical 两类——人来判也会犹豫。

绝大多数把 Jev 用砸的案例，都是拿着 choice 直接执行，不看 confidence。

阈值不能拍脑袋。跑一批你自己的真实数据，按置信度分桶统计准确率。模型宣称是校准的，0.7 那一桶长期就该在 70% 附近——这张表既是在定阈值，也是在验证它在你的数据上到底校不校准。

置信度低有两种成因，probabilities 能分辨：

  • 前两名咬得很紧——这条输入本来就跨两类。该上抛，或者承认你的分类体系有重叠。
  • 分布接近均匀——模型没抓到信号。多半是 state 信息不够，或判据写得太模糊。
ans = r.answers["department"]

if ans.confidence >= 0.85:
    route_to(ans.choice)            # 直接执行

elif ans.confidence >= 0.60:
    route_to(ans.choice, flag="需复核")

else:
    # 0.596 落在这里
    escalate(
        text,
        hint=ans.choice,            # 猜测一起带上
        confidence=ans.confidence,
    )

# 阈值怎么来：分桶验校准
#   0.5–0.6 → 实际准确率 ?
#   0.6–0.7 → 实际准确率 ?
# 对不上，阈值就是假的
中文场景至今没有公开评测，这一步不能省
06

输出免费，所以一次多问几个不花钱

同一次请求里的问题共享同一份 state，而 state 只按输入计费一次。

所以问 1 个问题和问 20 个问题，成本几乎一样。正确用法是反直觉的：把可能用得上的问题一次全问了，在代码里筛。

官方管这叫投机扇出。上限是 64k 上下文，其中 state 加最长的那个问题不超过 32k。

顺手把「以前因为太贵所以没问」的问题也加上——这一步经常能白捡新功能。
r = client.system_one(
    state=ticket,                # 只算一次钱
    questions={
        "department":   Choice(...),  # 这次要用
        "is_spam":      Noul(...),    # 这次要用
        "frustration":  Score(...),   # 这次要用
        "wants_refund": Noul(...),    # 可能用不上
        "is_urgent":    Noul(...),    # 可能用不上
        "needs_human":  Noul(...),    # 可能用不上
        "is_duplicate": Noul(...),    # 可能用不上
        "language":     Choice(...),  # 可能用不上
    },
)

# 组合逻辑在你的代码里，不在模型里
priority = "P0" if (
    r.answers["is_urgent"].noul > 0.8
    or r.answers["frustration"].score > 1.6
) else "P2"

07

问题只有三种，别的都是这三种拼出来的

原语问它什么返回典型用途坑
Choice 从这些选项里选一个 choice
probabilities
confidence		 意图路由、工单分派、选下一个点击的 DOM 元素、function calling 选项必须是闭集，单题上限 255 个。抽取类任务要先出候选再选
Score 在这个量表上打一个分 score（小数）
probabilities
confidence		 质量打分、情绪强度、优先级、重排序 一个 Score 只装一个维度。「代码质量」要拆成可读性 / 有无 bug / 测试覆盖
Noul 这句陈述为真吗 noul（0–1） 护栏、内容审核、语义检索、事实核对 instructions 写陈述句，不写问句
核心心法一句话：问题尽量原子，组合逻辑写在你自己的代码里
08

同一个分类任务，两种写法

用 LLM

prompt = f"""判断这个工单属于哪个组。
只输出 JSON，不要解释。
可选：billing / technical / sales
工单：{ticket}"""

resp = llm.chat(prompt)         # 逐 token 生成

# 然后你要处理这些：
text = strip_markdown_fence(resp)
try:
    data = json.loads(text)
except JSONDecodeError:
    return retry(prompt)         # 重来一次

dept = data.get("department")
if dept not in VALID:            # 它可能编一个
    return retry(prompt)

# 而且拿不到可信的置信度

用 Jev

r = client.system_one(
    state=ticket,
    questions={"department": Choice(
        instructions="这个工单该给哪个组",
        criteria=VALID,
    )},
)

dept = r.answers["department"].choice
conf = r.answers["department"].confidence

# 没有 json.loads
# 没有剥 markdown fence
# 没有重试分支
# 没有「它编了个不存在的值」
# 有一个能写 if 的 confidence
代价：它只会做判断。要生成文案、要解释理由、要多步推理，还得用 LLM。
左边那堆重试与校验分支，是这类任务最常见的技术债

先泼几盆冷水

「快 193 倍」出自 TypeSafe 自己的 workflow evals，官方也标注了那是收益上限。拿只做分类的模型和要生成完整回答的模型比延迟，本就不对等
正则可能更强上一页那份评测里，两行正则规则拿到 91.8%，比 Jev 最好的单信号（89.4%）还高。上新东西之前先跑传统基线
中文零公开数据训练语料未公开，中文任务的校准质量至今没有任何公开评测。别把英文结论直接搬到中文工单和审核上
幻觉 ≠ 判断正确「不可能幻觉」指的是输出不可能违反 schema、不可能编出你没定义的选项。选错依然会发生，靠置信度门控兜，不靠模型保证
官方公布了毛边docs 里有一页 Jev 1.13 jaggedness，列了已知失败模式。值得表扬，也意味着上生产前必须自己跑一遍你的数据
它的稳定优势是成本、延迟与抗分布漂移，不是绝对准确率
13

什么时候该用，什么时候别用

主场

  • 高频、重复、答案空间提前已知的判断
  • Agent 的每一步「选哪个元素 / 调哪个工具」
  • LLM 的输入输出护栏、内容审核
  • 无 embedding 的语义检索与重排序
  • 上下文剪枝：逐条判断该不该留

别用

  • 要输出文字、代码、摘要——它完全不会
  • 要解释理由——它只给概率
  • 要多步推理——问题之间隔离，天生没有链
  • 开放式抽取——得先出候选，再让它选
  • 一天只调几十次——省的钱抵不过多一个供应商
  • 窄任务且你有标注数据——先跑传统基线再说
一句话：把「其实只是选择题」的调用交给它，剩下的留给 LLM

怎么开始

没拿到 key 也能先写代码。官方出了一个接口完全一致的替身，后端换成普通 LLM API，代码结构先定下来，拿到 key 改一行 import。

不想排队就走 Vercel AI Gateway，模型 ID typesafe-ai/jev，已官方上线。

OpenRouter 有模型页，但截至本页更新日它的 /api/v1/models 还没列出该模型，调用前自己确认。

第一件事不是接入，是跑一遍置信度分桶表。阈值是量出来的，不是拍出来的。

pip install system-one-adapter

# 2. 拿到 key 之后
pip install typesafe-sdk

npm install @typesafe-ai/sdk
